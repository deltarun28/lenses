# Lenses

One practical thinking lens each day.

**→ [deltarun28.github.io/lenses](https://deltarun28.github.io/lenses/)**

Open it on a phone and add it to the home screen: menu → _Install app_ on
Android, Share → _Add to Home Screen_ on iOS.

Each lens is a decision tool — a mental model, framework or strategic concept —
written as a short field-manual entry with one or more worked examples from
military strategy, leadership and organisational decision-making, and building
products and businesses.

The app is a progressive web app. It installs to the home screen, works offline
for anything already loaded, requires no account, and stores your notes on your
own device.

## What it deliberately does not do

No streaks, points, badges, notifications, accounts, subscriptions, social
features, AI chat, or analytics. Adding any of these is out of scope — see
`AGENTS.md`.

## Setup

Requires Node.js 20 or later.

```bash
npm install
npm run dev          # http://localhost:3000
```

The service worker is disabled in development, so PWA behaviour must be checked
against a production build:

```bash
npm run build
npm run start
```

## Adding content

Lenses are Markdown files in `src/content/lenses/`, one per file, with YAML
frontmatter, four required `##` sections, and up to three optional worked-example
sections. Adding a lens is a content change only — no application code needs to
change.

Full instructions, including the exact section headings, are in
[`docs/content-authoring.md`](docs/content-authoring.md).

## How the daily lens is selected

The app stores one value: your local **start date**, set the first time you open
the app on a device.

- Day number = whole calendar days from the start date to today, plus one.
- Today's lens = the published lens at position `(day − 1) mod library size`,
  ordered by `sequence`.
- "Go to day N" rewrites the start date to `today − (N − 1) days`.

Because there is one stored value, the current day and the start date can never
disagree. All arithmetic uses local `YYYY-MM-DD` strings, never timestamps, so
daylight saving transitions cannot shift a day boundary.

Two consequences worth knowing:

- The sequence is **per device**. Two people who install on different days see
  different lenses on the same date. This is intentional — day 1 should be a real
  first day, not a date the app was published.
- Clearing site data resets you to day 1. The day setter on the home page is the
  recovery path: set your day again and the sequence continues.

The "day" is a suggested reading path, not a gate. Every published lens is
available in the library from the start.

## PWA behaviour

- Manifest generated by `src/app/manifest.ts`, served at `/manifest.webmanifest`.
- Service worker built by Serwist from `src/app/sw.ts` into `public/sw.js` at
  build time. `public/sw.js` is generated and git-ignored.
- One visit with a connection caches every published lens, the main pages and
  the app shell, so the app works offline afterwards. See `docs/offline.md` for
  the details, the limitations and the tests.
- No push notifications.

## Storage limitations

Observations and the start date live in `localStorage` under the `lenses.v1.`
prefix. That means:

- They stay on one device in one browser and are not synced or backed up.
- Clearing site data deletes them.
- Private browsing may discard them when the session ends.

Storage failures are handled rather than thrown: unavailable storage reads as
empty, and corrupt entries are discarded individually rather than losing the
whole set.

## Deployment

Every route prerenders — there are no route handlers, server actions or dynamic
functions — so the app can be served either as a static site or from a Next
server.

### GitHub Pages

Pushing to `main` builds and publishes the site through
`.github/workflows/deploy.yml`. Enable it once, under **Settings → Pages →
Build and deployment → Source: GitHub Actions**.

The site is served from a subdirectory, `https://<user>.github.io/<repo>/`, so
the build sets a base path:

```bash
NEXT_STATIC_EXPORT=true NEXT_PUBLIC_BASE_PATH=/lenses npm run build
```

`npm run build:static` wraps that and writes `out/`. The workflow derives the
base path from the repository name, so renaming the repository does not break
every asset URL.

Two things do not follow from the base path on their own, and both fail silently:

- **`.nojekyll`.** Without it, GitHub Pages runs Jekyll, which drops `_next/` —
  every script and stylesheet on the site. `build:static` and the workflow both
  create it.
- **Base path in non-routed strings.** Next applies the base path to `<Link>`,
  routing and the manifest link, but not to manifest contents, metadata icon
  URLs or the service worker's offline fallback. Those go through
  `withBasePath()` in `src/lib/base-path.ts` and are covered by
  `tests/unit/base-path.test.ts`.

To check the deployable artifact locally, including offline behaviour:

```bash
npm run build:static
npm run serve:static     # http://127.0.0.1:3100/lenses/
npm run test:e2e:static  # the full e2e suite against that artifact
```

### Vercel

Import the repository; the defaults are correct, and no base path is needed. The
build must run `next build` with webpack (`npm run build` already does this)
because the Serwist plugin injects the service worker through the webpack build.
